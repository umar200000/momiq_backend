# Current API contract

This document describes implemented behavior, not future checklist items. All API responses are JSON with `Cache-Control: no-store`. Errors use `{ "error": "user-facing message" }`; callers branch on HTTP status, not translated text. Dates are UTC ISO-8601. No monetary endpoint is implemented yet.

## Session lifecycle

- `POST /api/auth/login`: local/test login (or explicitly enabled isolated staging) accepts phone, code and optional `customer`/`sitter` role. Production rejects test login at configuration load. SMS remains deferred. Returns `token`, `userId`, `account`.
- Bearer tokens expire after seven days; there is no silent refresh. Multiple devices may remain signed in until expiry or revocation.
- `POST /api/auth/logout`: revokes this token. Mobile clears local data even when the network is unavailable; an offline server token expires normally.
- `POST /api/auth/logout-all`: revokes all client tokens for the authenticated account. Other accounts/admin sessions are unaffected. Mobile requires server confirmation before claiming success.
- Admin blocking revokes all client sessions. Unblocking requires a new login; old tokens do not revive.
- The app stores one credential envelope in OS secure storage, scoped to environment/API/user. Old plaintext preference tokens are discarded and require one fresh login. iOS Keychain records without matching installation metadata are discarded. Android backup/device transfer excludes private app data.

## Profile concurrency

`GET /api/me`, login and admin user listing return `account._revision` (integer, initially zero). Every full-account `PUT /api/me` must echo the revision from the snapshot being edited. Successful writes increment it and return the authoritative account.

Admin `PUT /api/admin/users/{id}` accepts `account` and/or `blocked`, plus top-level `_revision` from that user's account. Omitting `blocked` preserves its existing value. Both profile and block changes increment the same revision. A block-only edit never replaces a newer profile snapshot.

- `409`: stale revision; no mutation is committed. Reload and let the user reapply their edits. Never retry automatically with a fresh revision.
- `428`: missing revision; update the client and reload.
- `400`: invalid payload/revision.
- `401`: missing, expired or revoked token.
- `403`: disallowed access or blocked account.

The compare-and-increment and account mutation share a transaction. Polling does not authorize an already open edit form to overwrite changes from another device: forms keep their original revision. Account metadata is generated by the server and is not persisted from client JSON.

## Upgrade compatibility

Optional pet strings (`name`, `age`, `sex`, `breed`, `notes`, `otherType`) and address strings are normalized to strings on accepted writes, including missing/null optional values. Pet/address IDs must be non-empty and unique within the account. A pet age, when supplied, is an integer string in 0–100; sex is empty, `Erkak` or `Urg‘ochi`. Boolean coordinates and malformed nested objects are rejected. Media decoding/storage still has separate work outstanding.

Sitter account preferences share `notifications` (`orders`, `chat`, `video`) and `language` (`uz`, `ru`, `en`) with the customer role. Optional `sitterProfile.schedule` has seven boolean `days` starting Monday and integer minute offsets `start < end`, both 0–1439, with server-owned timezone `Asia/Tashkent`. Overnight intervals, blackout dates and booking availability are not yet implemented. A successful settings save must use the returned account/revision; do not copy local mock settings over server data.

This branch changes the write contract. Old applications/admin pages without `_revision` can read but cannot update profiles. Deploy the matching admin and mobile builds together in staging, then enforce a minimum supported app version before production rollout. Do not bypass the precondition to support old writers: that would restore lost-update bugs.

## Database upgrades

`migrations.py` applies ordered, checksummed migrations inside one SQLite write transaction. Repeated runs do nothing; altered history or a database newer than the application is rejected. Migration 1 adds account revisions without rewriting existing JSON, users, roles, chat or listings.

Dry-run uses a SQLite online backup (including committed WAL pages), never the source database:

```powershell
python migrations.py .local/preview/momiq.sqlite3
```

Before applying to a hosted database, stop writers, make an independent verified backup, and use a new backup path:

```powershell
python migrations.py <database> --apply --backup <new-backup-file>
```

Then start the matching application and run smoke checks. A code rollback does not roll back schema/data. Restore a database backup only with writers stopped and an explicit decision about writes since the backup. The production deploy script still needs the coordinated stop/backup/migrate/restart workflow installed on the host; this document does not claim it has been deployed.

Secure storage configuration follows the package maintainer's [Android/iOS instructions](https://pub.dev/packages/flutter_secure_storage). Actual iOS Keychain validation remains pending macOS/device access and final signing.

## Manual Paynet Xolis balance (migration 2)

All financial amounts are **integer minor UZS units**, 100 = 1 so‘m. Commission is integer basis points: 1000 = 10%, range 0–10000. No customer service payment, bank withdrawal or automatic payment-provider integration is exposed.

- `GET /api/wallet`: authenticated sitter's balance, latest 50 ledger entries and current QR/config. `balanceEligible` means only balance >= 1,500,000 minor units; catalog/booking eligibility is not yet connected.
- `GET /api/wallet/topups`: own request history. `POST` requires `requestId`, `amountMinor`, base64 `receipt`, displayed `qrVersion`, `termsVersion=balance-no-refund-v1`, and `acceptNonRefundable=true`. Pending request returns 201 without crediting balance. Identical retry returns 200; same ID/different payload or duplicate image hash returns 409.
- `GET /api/wallet/topups/{id}/receipt`: own receipt only; another sitter's ID returns 404.
- `GET/PUT /api/admin/platform-settings`: admin cookie; PUT requires loaded `version` and `reason`. Optional `commissionBps`, `qrImage`, `testOnly` append a version; stale version is 409. Production rejects test QR configuration. Old requests retain their QR version.
- `GET /api/admin/topups`: request metadata, never bulk receipt images. Optional `status=pending|approved|rejected|all`. Both topup lists return up to 20 records and `nextCursor`; supply `cursor` for the next page. Own-list cursors are ownership checked.
- `GET /api/admin/topups/{id}/receipt`: admin-only lazy receipt retrieval.
- `POST /api/admin/topups/{id}/review`: `decision=approve|reject`, nonempty `reason`. Approval additionally requires `fundsVerified=true`, exact `receivedAmountMinor` and unique `transferReference`. References are trimmed/uppercased. Status, ledger entry, balance and audit commit together. Repeating the same approval returns 200 without another credit; conflicting decision or reused transfer reference returns 409. Rejection never credits funds.

Ledger entries cannot be updated or deleted. Compensation must append a new entry; commission/reversal business routes are still outstanding. Seed cleanup refuses accounts with financial history; use a new isolated preview directory. Receipt photos remain private Base64 DB data pending object storage. Image hashes detect identical bytes; altered/fake/another person's receipt still requires manual verification against the actual provider statement. Draft persistence, receipt clarification workflow, recipient metadata and review notifications remain open.

## Image validation

Uploads are decoded using pinned Pillow 13.0.0: PNG, JPEG or WebP, at most 3 MiB, 12 million pixels, 8192 pixels per dimension, single frame. Both structural verification and full pixel loading must succeed. Fake magic headers and truncated images return 400. Decoder concurrency is bounded to two per process; saturation returns retryable 503. Original receipt bytes are retained for audit/hash matching; public media derivatives and EXIF stripping are still M104 work. Existing corrupt legacy images must be replaced when writing affected profiles. Validation follows [Pillow's image verification and decompression limits](https://pillow.readthedocs.io/en/stable/reference/Image.html).
