# Current API contract

## Liveness, readiness and release identity

`GET /api/health` is public process liveness and does not open or create a database. It retains `ok`, `mode`, `instanceId`, `sms`, `clientLoginEnabled` and `testLogin`, and adds `releaseSha`. A development checkout returns null for the SHA; an archived deployment reads its trusted `.release-sha` once when the worker imports the application. A subsequent symlink change does not make an old worker claim the new release. Missing SMS integration remains explicit.

`GET /api/ready` opens the existing SQLite database in read-only/query-only mode with a two-second lock timeout and a consistent read transaction. It checks the environment, the exact set of migration checksums and essential table/column reads. Success is `{ok:true, mode, releaseSha, schemaVersion}`; unavailable, missing, incompatible or unreadable data returns HTTP 503 with only `{ok:false}`. It never creates a missing database, migrates, logs in or writes business records. Neither endpoint proves disk writeability, complete database integrity, media/provider health, backup freshness or production eligibility. Both use `no-store` and `nosniff`.

## Audited booking oversight

`GET /api/admin/bookings` is admin-cookie-only and accepts the same strict `status`, `bucket`, `q` and `before` filters as participant booking indexes. It returns at most 20 rows in descending immutable sequence order. Search matches booking ID and frozen party names; it does not index private addresses, care notes, contact data or media. Customer/sitter tokens cannot use this surface.

`GET /api/admin/bookings/{id}` returns read-only frozen terms, role identities, current state/revision/deadline, the latest 30 booking events, related commission debit/refund journal entries and an optional dispute reference. It never impersonates a participant or enables generic state/amount editing. Exact addresses follow the existing booking status visibility policy. `/history?before=revision` and `/care?before=id` each page 30 immutable records; care is explicitly owner/sitter-reported information, not independently verified care. Authorized oversight remains possible when a participant has been blocked. Detail/history/care access appends actor/action/booking-ID/time to the audit, without copying private content; the read and audit share a transaction. POST/PUT/DELETE on these routes return 405 without changing bookings, balances or care. Policy-bound dispute decisions remain in the separate dispute API. Booking oversight and dispute decisions require the administrator role; support, moderation and finance operators cannot use these routes. MFA and hosted role acceptance remain M092 release work.

This document describes implemented behavior, not future checklist items. JSON API responses use `Cache-Control: no-store`; private media routes return authorized binary content. Errors use `{ "error": "user-facing message" }`; callers branch on HTTP status, not translated text. Timestamps are UTC ISO-8601; care-calendar days use Asia/Tashkent. Wallet amounts use integer minor units; customer service payments remain outside Momiq.

## Session lifecycle

- `POST /api/auth/login`: local/test login (or explicitly enabled isolated staging) accepts phone, code and optional `customer`/`sitter` role. Production rejects test login at configuration load. SMS remains deferred. Returns `token`, `userId`, `account`.
- Bearer tokens expire after seven days; there is no silent refresh. Multiple devices may remain signed in until expiry or revocation.
- `POST /api/auth/logout`: revokes this token. Mobile clears local data even when the network is unavailable; an offline server token expires normally.
- `POST /api/auth/logout-all`: revokes all client tokens for the authenticated account. Other accounts/admin sessions are unaffected. Mobile requires server confirmation before claiming success.
- Admin blocking revokes all client sessions. Unblocking requires a new login; old tokens do not revive.
- The app stores one credential envelope in OS secure storage, scoped to environment/API/user. Old plaintext preference tokens are discarded and require one fresh login. iOS Keychain records without matching installation metadata are discarded. Android backup/device transfer excludes private app data.

`POST /api/me/role` takes exactly `{role: "customer"|"sitter"}` under the existing client token. It idempotently enrolls only that caller in the requested self-service role and returns `userId`, selected `role`, all enrolled `roles` and current `account`. A new enrollment is audited once. It never changes profile revision, listings, identity verification, moderation, bookings, balances or session privileges; admin roles/other user IDs/extra fields are rejected. Existing blocked/deleted/expired-session checks apply. Role selection is a local navigation preference, not a global cross-device mode or an authorization grant. Mobile changes mode only after server success, invalidates outgoing stores and clears the navigation stack while retaining the same token and encrypted wallet retry drafts. Failed or late responses do not switch another session. Restart reopens the selected role and routes incomplete identity/sitter registration back to its form, prefilled with saved server fields. Unsaved keystroke drafts remain M124; sitter publishing still requires independent completeness/moderation checks.

## Sitter profile session boundaries

Sitter profile, availability, notification and language forms retain the API instance and session generation that loaded the account. They do not restore a different account at submit time. A replacement login or role generation invalidates subsequent submits and late responses; old GET/PUT results cannot update another account cache, global language or navigation. Disposed controllers and late photo-picking results are ignored. The sitter home profile refresh also rejects older overlapping reads. API-enabled sessions without credentials cannot silently fall back to mock profile data. These guards do not cancel an HTTP write already accepted by the original account's server, persist unsaved keystrokes or claim every other app screen has completed M124 acceptance.

Sitter registration follows the same bound API/session rule for initial account load, photo picking, submit and navigation. It preserves existing calendar/schedule fields when completing the sitter profile. A successfully saved profile response becomes the next retry's account snapshot/revision if a later listing-housing/cache step fails; already acknowledged profile data is not rolled back or falsely resubmitted using its original revision. Authenticated registration does not write preview `mock.profile` identity keys. Profile and listing saves remain separate server operations, with success navigation only after both return successfully.

`ListingStore` binds reads/writes to its session and reset generation, starting before preference restoration. Reset/disposal invalidates pending loads and mutations; an old load completion cannot clear the replacement load's future or mark it loaded, and an old mutation's cleanup cannot clear the replacement operation's busy state. Guards run after request/preference waits and before applying a result. A new session must reset or recreate the store; a stale store cannot acquire authority merely by starting another method call.

## Profile concurrency

The customer account store invalidates an older refresh as soon as a profile/pet/message mutation starts, including when the write finishes before the old read returns. A stale refresh cannot replace the account revision, archived pets, global account cache or language, or publish an obsolete error. Initial loads share one in-flight read and can retry after failure. Session generation and disposal are checked after API/cache waits; a stale caller cannot start another request, repopulate a cleared cache or report a successful save. An API-enabled build without credentials requires login instead of loading a mock account. This does not persist unsaved form keystrokes or undo a server write already accepted for the original account.

Concurrent credential restores share one API instance, wait for local logout cleanup and reject a credential read invalidated by logout or a replacement session. A delayed logout response is bound to its original API/session and cannot clear a replacement login. Startup account validation similarly discards old success/401/403 responses before cache updates or destructive cleanup; it offers recovery/retry if the session changed. These are client-side lifecycle guards, not token refresh or provider integration.

`GET /api/me`, login and admin user detail return `account._revision` (integer, initially zero). Admin index rows are noneditable summaries. Every full-account `PUT /api/me` must echo the revision from the snapshot being edited. Successful writes increment it and return the authoritative account.

Admin `PUT /api/admin/users/{id}` accepts `account` and/or `blocked`, plus top-level `_revision` from that user's account and a required nonblank `reason` of at most 1000 characters. Unknown fields and non-boolean `blocked` are rejected. Omitting `blocked` preserves its existing value. Both profile and block changes increment the same revision. A block-only edit never replaces a newer profile snapshot. The authenticated actor, reason, changed fields, before/after revision/block state and account hashes are audited atomically; audit failure rolls back profile, listing and session changes. Profile name changes additionally record old/new names and photo hashes, never raw photos or the entire account.

Legacy `DELETE /api/admin/messages/{id}` takes exactly `{reason}` with the same reason bounds. It redacts text/image and audits actor, reason and before/after hashes in the same transaction. Retrying an already redacted message succeeds without another audit entry. This legacy redaction is irreversible; no recoverable evidence/appeal archive is implied. These reason-required mutations need the contract-1 admin panel; older forms receive HTTP 400 and must reload the matching panel.

- `409`: stale revision; no mutation is committed. Reload and let the user reapply their edits. Never retry automatically with a fresh revision.
- `428`: missing revision; update the client and reload.
- `400`: invalid payload/revision.
- `401`: missing, expired or revoked token.
- `403`: disallowed access or blocked account.

The compare-and-increment and account mutation share a transaction. Polling does not authorize an already open edit form to overwrite changes from another device: forms keep their original revision. Account metadata is generated by the server and is not persisted from client JSON.

## Upgrade compatibility

### Canonical account shape

Release one supports dog/cat bookings only, for all three services. The sitter's chosen species further narrows that set; home visits no longer imply every species. `Boshqa` animals may remain in the private account but cannot be selected for a new quote/request or via restored mobile drafts. Existing confirmed agreements are not deleted by this rule. Listing API uses `dog`/`cat`, customer accounts/public listing projection use `It`/`Mushuk`. Booking policy exposes `supportedPetTypes`. Boarding/personal listing selects one species; home visit may select one or both. Personal booking capacity is always one. Listing location is required for residential/personal, optional for home visit, but any supplied location must validate (finite coordinates and non-empty address ≤1000 Unicode code points); mobile enforces the same limits.

Full-account writes use the same validator for owner and admin. Required text is trimmed and non-empty; limits below count Unicode code points before trimming. Unknown top-level/profile fields are not stored. Invalid types (including boolean-as-integer), missing required fields, duplicates and limits return 400 and leave both data and revision unchanged. Valid defaults below are materialized in the response, login and subsequent GET; creating a new login is the sole exception allowing an unfinished profile with empty first/last names.

| Field | Accepted value / default |
| --- | --- |
| `profile` | Required object: `first` and `last` strings, each 1–100 after non-empty check; `photo` validated image or missing/null → null. Names allow Unicode, spaces, apostrophes and hyphens. |
| `favorites` | Missing → []; array of known string sitter IDs, deduplicated in order. Archived/unavailable known contacts remain valid references, without granting booking eligibility. Null, objects and unknown IDs are rejected. |
| `addresses` | Missing → []; at most 30 objects, unique non-empty `id`, non-empty `address`; id/label/address/apartment strings ≤500, omitted/null optional label/apartment → ''. Finite numeric lat −90…90, lon −180…180, never booleans. |
| `notifications` | Missing → object; omitted orders/chat/video → true. Supplied values must be boolean; null object/flags rejected. |
| `language` | Missing → uz; exactly uz/ru/en. |
| `pets` | Missing → []; at most 30 including retained archived animals. Unique trimmed id ≤100; mandatory decoded photo and type It/Mushuk/Boshqa. Optional name/age/sex/breed/notes/otherType strings ≤2000; missing/null → ''. Other type requires non-empty otherType. Age/sex and care facts follow the rules below. archived defaults false on creation; existing archive state uses its dedicated endpoint. |
| `sitterProfile` | Missing/null → null; otherwise object. years missing/null or integer 0–80; about missing → '', string ≤4000 (explicit null rejected); homePhotos missing → [], max 9 validated non-null images; housing missing → apartment, enum apartment/house. Optional schedule rules below. |
| `support` | Legacy owner archive only, missing → []; max 100 objects with unique trimmed id (1–100) and non-empty trimmed text (≤4000). Unknown legacy fields are discarded, no delivery/admin status is inferred. New support messages use `/api/support`. |

All container fields require the documented object/array type; explicit null is only accepted where stated. An omitted optional pet care field preserves its previous value during owner updates; explicit empty/null clears it. IDs are normalized before this merge, so surrounding whitespace cannot bypass preservation or cause a server error. Media byte/pixel/type limits are documented in the upload section. Sitter profile editing accepts unspecified experience/about without inventing experience; customer and sitter name editors enforce the 100-code-point limit before sending. Existing legacy media that fails decoding is not silently accepted.

Optional pet strings (`name`, `age`, `sex`, `breed`, `notes`, `otherType`) and address strings are normalized to strings on accepted writes, including missing/null optional values. Pet/address IDs must be non-empty and unique within the account. A pet age, when supplied, is an integer string in 0–100; sex is empty, `Erkak` or `Urg‘ochi`. Boolean coordinates and malformed nested objects are rejected. Media decoding/storage still has separate work outstanding.

Sitter account preferences share `notifications` (`orders`, `chat`, `video`) and `language` (`uz`, `ru`, `en`) with the customer role. Optional `sitterProfile.schedule` has seven boolean `days` starting Monday and integer minute offsets `start < end`, both 0–1439, with server-owned timezone `Asia/Tashkent`. The enabled weekdays and inclusive hour endpoints apply only to arrival/departure, never every instant of care: an overnight stay may cross nonworking days. At an ending boundary of 18:00, 18:00:00 is allowed but 18:00:00.000001 is not. Null/missing schedule adds no hour restriction and does not guarantee vacancy or automatic acceptance. All-false days disable new handovers.

Optional `sitterProfile.closedDates` is a sorted unique list of at most 366 valid `YYYY-MM-DD` dates. Only the local **start date** of a new booking is blocked; ongoing care and departure may cross/fall on a closed date. Omitted closedDates from older clients preserves the saved calendar; an explicit empty list clears it. Account CAS protects concurrent edits. Schedule/calendar-only edits preserve a currently valid approved/suspended listing hash without reviving a stale approval; other public profile changes still require moderation. Existing accepted/active obligations are not cancelled or blocked by later schedule edits.

Quote creation, new request creation and pending acceptance check the current calendar under the write transaction before any commission debit. Exact retries of previously recorded actions retain their normal idempotency. `GET /api/sitters?startsAt=<zoned ISO>&endsAt=<zoned ISO>` filters by this same policy; both endpoints are required, unique, zoned, increasing and at most 365 days apart. Public listings include `availability` with schedule/closedDates/timezone and explicit `hoursApplyTo=endpoints`, `closedDatesApplyTo=start`, `overnightAllowed=true`. Without a date interval, `availabilityKnown=false`; with dates the capacity rules below apply. The app calendar and search use these server values and Tashkent time independent of the device zone. A successful settings save must use the returned account/revision; local mock settings never overwrite server data.

The mobile availability card requires both `availabilityKnown=true` and an integer `freeCapacity` in 0–30. Missing or invalid capacity is shown as unconfirmed; it never falls back to locally inferred booking counts. Zero home-visit capacity is unavailable. Capacity, weekdays, handover/overnight rules and the non-reservation explanation are localized in Uzbek, English and Russian; displayed interval times remain Tashkent time.

### Discovery pages and availability

`GET /api/sitters` returns at most 20 `sitters`, opaque `nextCursor` (null when exhausted), and server `asOf`. Pass the cursor as `after` with the same filters. Ordering is stable by `(userId, service)`; removed/paused/underfunded listings are rechecked on every page, and refresh starts a new traversal. A cursor is a read-only position, not an authorization grant or a reservation. It is bound to normalized filters and, for favorites, the authenticated account. Unknown/duplicate/malformed query parameters are 400. Each page uses one DB read snapshot. Older clients without cursor handling see only the first page; the production rollout requires the matching mobile version.

Optional filters: `service=boarding|homeVisit|personal`, `pet=cat|dog`, integer UZS `minPrice`/`maxPrice` (0–999999999), `animals` (1–30, default 1), `verified=0|1` (actual identity verification only, TEST approval never qualifies), `minRating=0|4.8`, `q` (public name case-insensitive substring, max 100), and paired future zoned `startsAt`/`endsAt` (up to 365 days). `favorites=1` requires a valid client bearer session and reads only that account's saved listing IDs; it never restores an ineligible listing or searches other accounts' favorites. Street addresses, phone, pet/care details and private media are not search fields.

With dates, eligibility uses the sitter calendar plus the same capacity calculator used under the acceptance write lock. Accepted/active/disputed overlapping care reduces capacity using **peak occupancy**, not the sum of disjoint stays. Adjacent intervals do not overlap. Different services and overlapping home visits are exclusive; an overdue active stay conservatively blocks new care. Pending/expired/rejected/cancelled requests do not reserve capacity. A matching result includes `availabilityKnown=true`, integer `freeCapacity`, and `availabilityInterval` (UTC endpoints); without dates no vacancy count is invented. This does not reserve a place or bypass owner-animal conflicts, balance or acceptance checks. The app displays the server count and Tashkent dates, pages on demand, deduplicates IDs, preserves existing rows on page failure, and discards late responses after filter/session changes.

Optional paired `lat`/`lon` must be finite and within ±90/±180. Both mobile and server quantize the search origin to two decimals; the server computes Haversine distance using only the already-public two-decimal listing point, never private home coordinates. `distance` is approximate straight-line kilometers (one decimal), with `distanceApproximate=true`; missing origin/listing point yields null/false. With an origin, the entire eligible catalog is ordered by `(distance, userId, service)`, unknown distances last, with a bounded 21-entry heap. The cursor also binds origin and distance position. This scans eligible listings per proximity page; indexing/load optimization remains M099/M131. Changes to listings between pages can require refresh; this is not a multi-request snapshot.

`region=tashkent` is the sole supported region/default. Without GPS the app offers the Toshkent catalog and no distance; this does not certify the unimplemented city polygon (M001/M029). Optional `maxDistance` (1–50 km) requires coordinates and is only a customer search preference; unknown distances remain visible with an explicit explanation. There is **no sitter service radius and no homeVisit distance rejection inside Toshkent**. No route length or travel time is claimed. Exact city-boundary booking enforcement remains a release gate.

### Operator account and listing indexes

`GET /api/admin/users` and `/api/admin/listings` require the admin cookie and return at most 20 metadata rows (`users` or `listings`) and `nextCursor`. Send it as `after` with the same filters. User order is stable by ID; listing order by `(userId, service)`. Query `q` searches ID, current public name and phone (max 100); private addresses, care notes and pet details are excluded. Users accept `role=all|customer|sitter` and `status=all|active|blocked`; listings accept `service=all|boarding|homeVisit|personal` and moderation `status=all|draft|pending|approved|rejected|suspended|archived`. Unknown, repeated or cross-kind filters/cursors are 400. All pages are read snapshots. Stats in the panel explicitly count loaded rows, not all matching accounts.

Rows have `_summary=true`. User `account` contains only name fields and null photo; it is **not an editable account document**. Listing indexes omit private location and media. `GET /api/admin/users/{id}` returns `{user, sitters}` with the full account/revision and names of that account's existing legacy chat contacts. `GET /api/admin/listings/{userId}/{service}` returns `{listing}` with the current listing revision, private address, completeness and actual moderation state. Each successful detail read appends operator/action/target/time to audit without private content. The panel loads detail before enabling edit/review forms, rejects stale responses after selection/filter changes, and retains rows plus a retry on page failure. Existing mutation CAS/reason rules remain mandatory; there is no summary-based blind write.

The admin top-up queue now includes minimal `owner={name,phone}` per record, independent of the currently loaded accounts page; client top-up responses do not include this operator metadata. Receipt evidence still loads separately. Personal operator accounts/RBAC and broader audit policy remain M092/M097.

This branch changes the write contract. Old applications/admin pages without `_revision` can read but cannot update profiles. Deploy the matching admin and mobile builds together in staging, then enforce a minimum supported app version before production rollout. Do not bypass the precondition to support old writers: that would restore lost-update bugs.

## Database upgrades

`migrations.py` applies ordered, checksummed migrations inside one SQLite write transaction. Repeated runs do nothing; altered history or a database newer than the application is rejected. Migration 1 adds account revisions without rewriting existing JSON, users, roles, chat or listings.

Dry-run uses a SQLite online backup (including committed WAL pages), never the source database:

```powershell
python migrations.py .local/preview/momiq.sqlite3
```

Before applying to a hosted database, stop writers, make an independent verified backup, and use a new backup path:

```powershell
python migrations.py <database> --apply --backup <new-backup-file>
```

Then start the matching application and run smoke checks. A code rollback does not roll back schema/data. Restore a database backup only with writers stopped and an explicit decision about writes since the backup. The production deploy script still needs the coordinated stop/backup/migrate/restart workflow installed on the host; this document does not claim it has been deployed.

Secure storage configuration follows the package maintainer's [Android/iOS instructions](https://pub.dev/packages/flutter_secure_storage). Actual iOS Keychain validation remains pending macOS/device access and final signing.

## Manual Paynet Xolis balance (migrations 2, 4–7)

All financial amounts are **integer minor UZS units**, 100 = 1 so‘m. Commission is integer basis points: 1000 = 10%, range 0–10000. No customer service payment, bank withdrawal or automatic payment-provider integration is exposed.

- `GET /api/wallet`: authenticated sitter's balance, latest 50 ledger entries and current QR/config. `balanceEligible` means only balance >= 1,500,000 minor units; catalog and first-chat eligibility also require this threshold; booking acceptance is still pending.
- `GET /api/wallet/topups`: own request history. `POST` requires `requestId`, `amountMinor`, base64 `receipt`, displayed `qrVersion`, `termsVersion=balance-no-refund-v1`, `acceptNonRefundable=true`, and at least one of `payerReference` or explicitly zoned `paidAt`. Pending request returns 201 without crediting balance. Identical retry returns 200; same ID/different payload or duplicate image hash returns 409.
- `GET /api/wallet/topups/{id}/receipt`: own receipt plus `revision` and original `paymentSnapshot`; another sitter's ID returns 404.
- `GET/PUT /api/admin/platform-settings`: admin cookie; PUT requires loaded `version` and `reason`. Optional `commissionBps`, `qrImage`, `recipientName`, `paymentInstructions`, `qrActive`, `testOnly` append a version; stale version is 409. Production rejects test QR configuration. Old requests retain their QR version.
- `GET /api/admin/topups`: request metadata, never bulk receipt images. Optional `status=pending|needs_info|approved|rejected|all`. Both topup lists return up to 20 records and `nextCursor`; supply `cursor` for the next page. Own-list cursors are ownership checked.
- `GET /api/admin/topups/{id}/receipt`: admin-only lazy receipt retrieval.
- `POST /api/admin/topups/{id}/review`: loaded `revision`, `decision=approve|reject|request_info`, nonempty `reason`. Approval additionally requires `fundsVerified=true`, exact `receivedAmountMinor` and unique `transferReference`. References are trimmed/uppercased. Status, ledger entry, balance and audit commit together. A missing revision returns 428; a stale revision returns 409. Repeating the same unchanged decision returns 200 without another credit; conflicting decision or reused transfer reference returns 409. Rejection never credits funds.

Ledger entries cannot be updated or deleted. Compensation must append a new entry; commission/reversal business routes are still outstanding. Seed cleanup refuses accounts with financial history; use a new isolated preview directory. Receipt photos remain private Base64 DB data pending object storage. Image hashes detect identical bytes; altered/fake/another person's receipt still requires manual verification against the actual provider statement. Encrypted device-bound drafts are implemented in the app; clarification, recipient snapshots and transactional in-app review notices are implemented. External push remains pending.

- `GET /api/wallet/topups/{id}`: current owner-scoped metadata, including revision and status.
- `POST /api/wallet/topups/{id}/amend`: only `needs_info` or `rejected`; requires current `revision`, a new stable `requestId`, complete valid evidence/payer metadata and renewed consent. Original `qrVersion` cannot change. Appends `pending` revision without credit; an identical retry returns the current row, changed retry is 409.
- `GET /api/{wallet|admin}/topups/{id}/history?before=<revision>`: up to 20 immutable evidence/decision revisions; `nextCursor` continues history. Admin includes actor identity. `GET .../history/{revision}/receipt` lazily returns that revision's private image. Replaced evidence hashes remain claimed by the original request.

Operators must compare recipient, time, amount and the provider's unique incoming transfer reference against the actual provider statement. An image, payer-entered reference, or matching visual appearance is not proof of funds. Re-encoded/cropped images can have different hashes; the verified incoming reference is unique across all sitters, with atomic approval protecting concurrent reviews. Do not invent another reference to bypass a duplicate conflict. If details differ, request clarification instead of crediting.

## Image validation

Uploads are decoded using pinned Pillow 13.0.0: PNG, JPEG or WebP, at most 3 MiB, 12 million pixels, 8192 pixels per dimension, single frame. Both structural verification and full pixel loading must succeed. Fake magic headers and truncated images return 400. Decoder concurrency is bounded to two per process; saturation returns retryable 503. Original receipt bytes are retained for audit/hash matching; approved catalog images use resized, oriented public derivatives stripped of EXIF; other media lifecycle work remains in M104. Existing corrupt legacy images must be replaced when writing affected profiles. Validation follows [Pillow's image verification and decompression limits](https://pillow.readthedocs.io/en/stable/reference/Image.html).


## Legacy support conversation attribution

The existing `/api/messages` and admin reply endpoints now expose server-derived `senderRole=customer|support`. The legacy backend has no real sitter-authored messages; admin responses must display as Momiq support, never as the sitter. A caller-supplied sender role is ignored. Reusing an existing request ID requires the same sender side, conversation, text and image; changed payload returns 409. The admin composer reuses its in-memory request ID after a failed response, until content changes or succeeds. The new participant conversation API below is separate. Legacy support history is retained; operator permission scoping and moderation remain open.


## Participant conversations (migration 8)

- `POST /api/conversations` with canonical `listingId=userId:service` creates or returns the unique customer/sitter/service conversation. New contacts require the customer role, first/last name and currently discoverable approved sitter listing (including >=15,000 UZS balance). Self-contact is rejected. Existing conversations remain accessible below the balance threshold. Booking-specific linkage is not yet implemented.
- `GET /api/conversations?before=<activity:sequence>` returns up to 30 own conversations and `nextCursor`, sorted by latest server message sequence, then conversation sequence. Snapshots expose only the peer's first name/last initial, service, last message metadata, unread count and `peerReadThrough`; no phone or address. Refresh the first page for new activity; deduplicate IDs when combining pages.
- `GET /api/conversations/{id}/messages`: latest 30 messages, chronologically ordered. `before=<id>` loads older history; `after=<id>` returns the next 30 in ascending sequence. They are mutually exclusive. `hasMore` describes that direction. Global integer IDs are monotonic; timestamps do not establish ordering. The response includes current conversation/read metadata. An empty page is valid.
- `POST .../messages` requires a stable 16–100 character alphanumeric/underscore/hyphen `requestId`, text <=4,000 characters and/or a bounded validated image. Sender identity/role is derived by the server, never trusted from the body. `(sender, requestId)` is unique; an identical retry returns the original message, changed content or conversation is 409. Create/send/read operations are transactional. Limits per account/minute: 10 new conversations, 60 messages and 10 image messages. Known identical retries do not spend quota. A blocked account cannot send; another participant can retain history but cannot send to it.
- Message pages expose `hasImage`, never bulk base64. `GET .../messages/{messageId}/image` loads an attachment only for a participant of that exact conversation. Strangers receive 404 for thread, history, image, send and read operations.
- `POST .../read` with `throughId` requires an existing message from that conversation. The read marker only advances; an older device acknowledgement cannot clear later arrivals. “Sent” means the server accepted the message, not that the peer device received it. “Read” is the peer's persisted acknowledgement.

The app uses this API for both role inboxes and a listing contact button. Active chat fetches delta pages every five seconds; the active inbox refreshes its first page every ten seconds. Background/covered routes do not poll. The former global three-second full account/message poll is removed. An outgoing request is encrypted before POST using account/API/conversation-bound storage; lost response/restart reuses exact content and ID. Local sends do not advance the incoming delta cursor (otherwise a concurrent incoming message could be skipped). Unsubmitted typing/image selection is still in memory; durable persistence starts on Send. Images load on demand and are not exported to the gallery.

Migration 8 creates new tables without importing legacy admin messages as sitter messages. Seed cleanup refuses fixture accounts with any new conversation history. Booking context, push, physical device chat verification and full operator role separation remain open; this is not a public-release-ready chat claim.


## Chat safety (migration 9)

`POST /api/conversations/{id}/block` accepts boolean `blocked` and the loaded `revision` from `blockRevision`. The authenticated participant controls only their own block. Blocks apply to the account pair across services, stop both directions of new messages and prevent opening another service conversation. They do not erase history or cancel bookings. `blockedByMe` and aggregate `canSend` are returned in the summary; the peer's independent block is not cleared by unblocking yours. Identical previous-version retry succeeds; stale conflicting changes return 409. Already-accepted message retries return the original result without redelivery.

`POST .../reports` requires an incoming message ID from that conversation, a reason <=1,000 characters and stable request ID. Own or foreign messages cannot be reported through this route. A reporter/message pair is unique; exact retries do not duplicate reports, changed evidence/reused ID returns 409. Initial report and immutable history commit together; 10 new reports/account/minute. `GET .../reports?before=<id>` returns only the caller's reports, 20 per page, with status, revision and moderator reason. Reporting alone does not block the peer.

Admin cookie endpoints:

## Booking transaction core and local/test API (migration 10)

The owner approved `elapsed-24h-v1` on 2026-10-28: each started 24 hours is one billable day (16h/24h = 1, 25h = 2). Integer microseconds avoid float boundary errors. Home visits use the per-animal daily price regardless of time spent during a visit; no fixed visit count/duration or hourly surcharge is promised. Both caller and database environments must be local/test. Production and hosted staging still fail closed while the remaining service lifecycle is integrated. Quotes expire after ten minutes or at the service start, whichever is earlier; an already submitted booking retains its agreed amount.

The server reads owned pets, approved listing price, capacity and versioned commission, and freezes integer-minor-unit totals, per-animal rates, dates, care text, pet metadata and private handover address. Migration 11 stores immutable private photo/passport objects by hash and links them to the quote; snapshots expose only `hasPhoto`/`hasPassport`. Quotes are immutable; quote views reveal only the city. A quote produces at most one booking even across different retry keys. Every mutation uses a fresh `BEGIN IMMEDIATE` transaction; the connection context commits or rolls back the booking, event, request fingerprint, audit and wallet journal together. Callers must not catch an error inside that context and commit a partial operation.

Acceptance rechecks eligible accounts/listing, pair blocks, threshold `max(15,000 UZS, commission)`, peak interval occupancy and cross-sitter animal conflicts. Pending requests do not reserve capacity. Intervals are half-open; differing services conservatively cannot overlap until their shared scheduling rules are approved. Accepted bookings retain quoted rates/settings when new rates/settings are published. Zero commission still requires the 15,000 UZS threshold and does not create a zero-value ledger entry.

Pending reject/cancel/expiry charge nothing. Prestart accepted cancellation appends one internal commission reversal, frees the reservation and records the reason. Automatic cancellation at/after start is refused for admin review. There is no customer service-money refund or payout. Retrying an accepted action returns current booking state; changed payload/reused action ID or stale revision conflicts. Expiry is persisted in bounded batches and on attempted pending actions, surviving restarts. The local/test server starts the persisted-deadline worker described below. Exact handover address is visible only in accepted/active/completed/disputed participant views; cancelled/pending views redact it. The mobile request/list/detail/accept/reject/cancel paths are connected behind the catalog `bookingEnabled` flag. In-app notifications, two-party service confirmation and no-show adjudication are described below; external push and final retention remain open. Home visits conservatively allow only one overlapping customer interval; a finer visit-slot scheduler is not implemented.

Migration 10 adds empty tables without changing existing account, wallet or chat rows. Seed cleanup refuses even an uncharged quote so booking history cannot be removed through fixture cleanup. Migration 10/11 were dry-run and then applied with the preview writer stopped and a fresh backup; the previous 27 tables remained unchanged. Subsequent migration evidence is recorded in the checklist; the current preview is schema 17.

### Approved state ownership and deadlines

| From | Trigger / responsible party | Result / deadline | Commission |
|---|---|---|---|
| Quote | Customer submits owned valid quote | Pending; reply deadline = earlier of creation + 2h and service start | None |
| Pending | Assigned sitter accepts before deadline, after fresh eligibility/capacity/balance checks | Accepted | Frozen commission debited once |
| Pending | Assigned sitter rejects, or either participant cancels with reason | Rejected / cancelled | None |
| Pending | Server deadline reached | Expired, including acceptance attempted at the exact boundary | None |
| Accepted | Either participant cancels strictly before start | Cancelled; under 24h is a confirmed late cancellation, with emergency review available | Full charged commission returned internally |
| Accepted | Each participant separately confirms start in `[start,end)` | First stays accepted; second becomes active | None |
| Accepted | Server reaches start + 15 / 30 minutes without both start confirmations | Contact reminder / ability to report no-show; never an automatic finding | None |
| Active | Each participant separately confirms completion at/after actual start | First stays active; second becomes completed; early mutual completion allowed | No price recalculation/refund |
| Accepted / active | Participant reports eligible no-show / service dispute | Disputed; administrator review due within 48h; start/complete frozen | No money moves on report |

Completion, no-show liability and overdue dispute resolution are never automatic. Three distinct confirmed late cancellations/no-shows within 30 days require operator review; emergencies are excluded, no automatic fine/block. A new confirmation cannot be invented for a late handover, and continuing a dispute does not extend dates. Terminal records are retained; exact retries are idempotent. Customer-to-sitter service money is never handled/refunded by Momiq. These state rules are implemented/tested in isolated HTTP/core tests; blocked native two-party M055 verification and public production activation remain separate release gates.

### Booking notices and expiry

Every committed booking event atomically creates one `kind=booking` in-app notification for each participant. The target is the booking ID and the source includes the booking revision and recipient; retry cannot duplicate notices or balances. Notice failure rolls back the booking event and wallet mutation. No external push/SMS is sent by this path.

The local/test server starts a booking expiry worker on startup, checks every 30 seconds, and commits at most five batches of 200 due requests per tick. Restart catches up from persistent deadlines. A transient failure rolls back that batch, logs only its exception type and retries next tick. Hosted staging/production remain gated. Acceptance also checks the deadline atomically. Detail reads expire their exact booking, so other accounts' backlog cannot postpone that check. Pending requests do not reserve capacity. Each tick also processes at most five batches of 200 accepted bookings for each no-show reminder stage: at 15 minutes (`contact_reminder`) and at 30 minutes (`complaint_available`). Each stage creates one atomic in-app notice per participant, uniquely keyed by booking/stage/recipient; no booking revision, incident, status or ledger mutation occurs. An incomplete two-party start confirmation is described as incomplete, never as proof that somebody failed to arrive. Active/disputed/terminal bookings receive no new no-show alert. A restart after 30 minutes skips the stale contact-stage alert and delivers only the actionable reporting prompt. Concurrent workers/retries cannot duplicate notices, and recipient failure rolls the batch back. Opening the notice only marks it read and opens the authenticated booking; the separate dispute flow still requires a participant report and admin evidence review. External push remains deferred to M081–M085.

### Two-party service confirmation (local/test)

`POST /api/bookings/{id}/start` and `/complete` use the same revision and stable request ID protocol as other booking actions. Either stored participant may confirm only for themselves. Detail responses expose `confirmations.start` and `confirmations.complete` with `mine`/`peer` flags; each confirmation is a new immutable event and atomic participant notice.

A start confirmation is accepted only while the booking is `accepted` and the server clock is within `[startsAt, endsAt)`. The first confirmation keeps `accepted`; the second changes it to `active`. Late handover beyond the agreed interval requires a separate admin review, which remains under development. A completion confirmation requires `active`; the first keeps it active, the second changes it to `completed`. Completion before the scheduled end requires both parties and does not recalculate the agreed price or create a refund. The service is never completed by the expiry worker. Disputed, cancelled or otherwise incompatible statuses cannot be completed through these endpoints.

An active booking past its scheduled end conservatively blocks that sitter's new acceptance until completion/review; an animal in overdue active care cannot be accepted elsewhere. Existing obligations and their chat remain available. No extra commission is charged by start/complete, and request replay cannot add another confirmation.

### Shared JSON transport limits

All JSON mutation bodies require exactly one decimal Content-Length (1–32,000,000 bytes), exactly one Content-Type with media type application/json, UTF-8 and a top-level object. Transfer-Encoding is not accepted on these API routes. Duplicate keys (including escaped-equivalent keys), NaN/Infinity, overflowing floats, nesting beyond 64 containers and incomplete/malformed JSON return 400. Wrong media type returns 415; a zero/oversize declared body returns 413. Up to two readers per process hold the read/decode permit; contention after one second returns 503. The body is read in 64 KiB chunks with a 60-second elapsed budget and a 30-second maximum socket wait for local HTTP; timeout returns 408. Invalid/partial bodies close the local HTTP connection instead of reusing unread bytes. Hosted WSGI shares validation and elapsed checks, but interruption of a blocked WSGI read depends on the proxy/server transport timeout; real hosted configuration acceptance remains M113. Video uploads retain their separate binary transport, validation and limits.

## In-flight authorization and login counters

After successful authentication, the request connection retains the authenticated principal and a transaction authorization callback. Each explicit BEGIN revalidates the same session, expiry, account block state and current operator route permission. For BEGIN IMMEDIATE this happens AFTER acquiring the writer lock. Current implicit INSERT/UPDATE/DELETE/REPLACE and executemany request paths first acquire an immediate transaction and revalidate. Failure rolls back before business writes. Authenticated request SQL scripts are rejected; application SQL remains fixed internal code, not a user-supplied SQL interface. Background jobs, initial login/bootstrap and independent database connections do not inherit a request principal.

This prevents a revoked/expired client from completing a slow profile save, a disabled/downgraded/recredentialed operator from completing a queued redaction, and a revoked finance operator from crediting a pending receipt. Profile revision, message evidence, balances, journal/audit/notifications remain unchanged on rejection. Existing valid requests and idempotent financial retries still use their established transactions. Authorization is checked at transaction acquisition, not continuously: a transaction that acquired its snapshot/writer lock before revocation can finish in that order. This does not cancel committed operations, rewind already sent responses, replace object ownership checks or claim every native/hosted boundary has completed acceptance.

Existing login counters remain 15 attempts per IP key per 60-second window, but now their read/increment is serialized under BEGIN IMMEDIATE. Parallel callers cannot overwrite one another's counts; expired windows reset at the exact boundary and independent keys remain independent. SMS provider/OTP delivery is still deferred. Reverse-proxy IP trust, distributed limits and full hosted abuse testing remain release work.

## Transient database contention and request diagnostics

SQLite BUSY/LOCKED primary or extended result codes now produce HTTP503 with a generic user-facing message. Other operational/storage failures remain HTTP500 with no raw SQL/path details. A 503 is not proof that no earlier transaction in a multi-stage request committed; retry a financial/booking/message mutation only using its original idempotency identity and payload. No automatic financial replay was added.

Native and WSGI handlers emit one `event=http` JSON record per dispatched request with allowlisted `method`, coarse `group`, numeric `status`, `durationMs` and `outcome`. Duration covers application dispatch/response preparation, not proxy queues or delivery of all bytes to the client. Logs omit raw paths/IDs, queries, IPs, credentials, headers, bodies and exception text. Readiness, scoped metrics and work-queue routes have fixed group labels. Existing Nginx/Gunicorn access logs are separate transport records, not extra application request counts. External collection, alerts, log retention and mobile crash reporting remain M116/M108 work.


## In-app notification acknowledgements

`GET /api/notifications` returns at most 20 newest-first owner notices, `nextCursor` (last returned decimal ID when more exist, otherwise null), and the owner's current `unreadCount`. The only permitted query is one optional `before` positive decimal ID (up to 18 digits). Empty, duplicate or unsupported filters return 400. Items include `id`, `kind`, `targetId`, `status`, `reason`, `created` and nullable `readAt`.

`POST /api/notifications/{id}/read` requires `{}` and no query. It returns `{ok:true,readAt,unreadCount}` from the committed owner-scoped write. The first read timestamp is stable on retries; the unread count is a snapshot at that transaction, so another device can change it between requests. An unknown/other-owner ID returns 404; client-supplied timestamps, counts and owner fields are rejected before mutation. Reads do not send external push or modify the source decision.

The app validates a complete page before replacing displayed history/cursor. Invalid refreshes retain the previous history and show retry. Acknowledgements update the displayed timestamp/count only after validation. For compatibility, a legacy server response containing only `{ok:true}` retains the old local count estimate until refresh; partial extended acknowledgements are rejected. New server responses are authoritative snapshots, not a continuously synchronized badge.

Loads, read receipts, errors, busy state, dialogs and internal navigation are tied to the originating API/session generation. Rebinding the page removes its owned old dialog; a session-invalid page hides history on rebuild. Listing notices create their own authenticated store rather than relying on a global instance. Unknown future kinds are inert generic notices and never URLs. Long dialog titles/content scroll at enlarged text sizes. External push, OS delivery/deep links and real-device lifecycle acceptance remain open.


## Participant chat envelopes and stale private views

Participant conversation creation accepts only `listingId`; message writes accept only `requestId`, optional `text` and optional `image`; delivery/read acknowledgement accepts only `throughId`. Blocking accepts only `blocked` and `revision`; reporting accepts only `messageId`, `reason`, `requestId`. Existing mandatory-field validation, ownership, revisions and exact-retry semantics remain unchanged. Unknown JSON keys, including caller-supplied sender/owner/status, return 400 before business/receipt/quota/notice mutation. The legacy `/api/messages` API has its separately documented compatibility contract.

Conversation index reads allow only one `before`. Message reads allow `before` or `after`, plus optional `changesAfter`; duplicates, unknown keys and invalid/empty cursors fail. Detail/image reads take no query; participant report history accepts one valid `before`. Related-booking reads retain the booking-index filter contract. Participant chat writes, support writes, review moderation and JSON booking writes reject query overrides. Binary video upload retains its explicit metadata query; it was not converted to a JSON envelope.

Mobile receipt-history/correction pages validate all display fields and cursor identity before replacing prior content. Malformed pages preserve existing history/totals with retry. Loads, receipts, dialogs, amendment navigation and finalizers retain the original API/session/top-up identity; changing only a target cannot revive an expired account. Receipt content is bounded before decoding and decode errors remain visible and retryable.

Operator profile/QR/receipt/correction/support forms and private evidence retain their source view. Late replies cannot reopen an obsolete panel, old file selections cannot replace newer attachments, and obsolete errors/finalizers do not change the current view. Selecting a QR/profile image blocks submit until its current read completes. Cancellation/removal invalidates the pending selection. Server-accepted requests still commit normally for their original principal; these UI guards neither reverse a committed operation nor substitute for server permissions.
